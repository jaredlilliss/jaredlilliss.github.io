What the collection actually looked like

Every bar is one day, and its height is how many of the 96 possible readings were captured. This is the honest version: for its first month the collector ran on a Windows laptop, which suspends background processes when it idles, so most days are partial and five have nothing at all. On 23 August it moved to an always-on host. Nothing after that is missing.

You can tell which machine took a reading by looking at the clock

The always-on host runs on a fifteen-minute cron schedule, so its readings land at exactly :00, :15, :30 and :45 — 24 of each, 96 a day, never drifting. The laptop ran a sleeping loop, so its readings landed wherever it happened to wake: :02, :11, :26, :39.

The cutover day has 115 readings rather than 96 — the 96 clean quarter-hour ones from the new host, plus 19 drifting ones from the laptop still running alongside it. Both collectors were live for a few hours. No reading was ever double-counted: across all 77,000 rows there is not one duplicate of the same hospital at the same instant.

Where this comes from. A privacy-by-design pipeline: no tables, columns or fields for people, accounts, sessions or devices exist anywhere in the schema — the privacy posture is structural, not a policy. Readings are collected every fifteen minutes on an always-on host and appended to a PostgreSQL time series that is never rewritten. The upstream feed serves current state only, with no historical endpoint, so a missed reading can never be backfilled — which is why the collector was built before any interface. —
